### 2026-08-05 — Phase 1 (slice 5): `create` command + `mkdir` sugar

The original spec's command list (`cd`/`mv`/`cp`/`ls`/`find`/`@`/`#`) never covers creation, and neither Linux nor Discord transfers directly: Linux's `touch` infers type from a filename extension, which we don't have for `server`/`chat-channel`/`voice-channel`; Discord has no command line for structure at all, only a right-click → modal type-picker. Landed on Discord's "type is always explicit" rule expressed as a command-line verb.

- **`create <type> <name>` (`lib/command-line/parse.ts`, `execute.ts`)** — creates a Node of the given type under the current directory. `<type>` accepts a few user-facing aliases (`folder`/`dir`, `server`, `channel`/`chat`, `voice`/`vc`) mapped onto `NodeType`; the rest of the line is the name (spaces allowed, no quoting needed — same convention as `cd`). Refuses to create inside a non-container node (a channel or document), same rule `mv`/`cp` already enforce via `isContainer`. `document` is deliberately excluded — it needs a `storageKey`/`mime` payload only a file upload can supply — so it's out of scope until uploads land.
- **`mkdir <name>`** — sugar for `create folder <name>`, kept because "folder" is the one type-inference case that genuinely is unambiguous, matching Linux muscle memory.
- **`CURRENT_USER_ID` (`lib/session.ts`)** — added alongside the existing `CURRENT_AVATAR_ID` stand-in (matches seed `user-bob`) so created nodes have an `ownerId` until real identity/auth lands.
- Both new commands return the existing `info` `CommandResult` (same as `mv`/`cp`), so the results dropdown and cache-invalidation wiring in `use-command-line.ts` needed no changes.
- **Scope for later slices:** permission-aware gating on create (no write-permission check yet, consistent with `mv`/`cp`), duplicate-sibling-name handling (pre-existing gap shared with `cp`), and `document` creation once file upload exists.
- Verified: `typecheck`, `lint`, `build`, and `pnpm test` (new parse/execute cases) all green.

### 2026-08-05 — Phase 1 (slice 7): `rm` command, with confirmation and real permission checks

The last command-line gap: the original spec never covers delete either. Landed on Linux's `-r` convention (bare `rm` refuses a non-empty folder/server; `-r` says "yes, and everything inside") plus a mandatory confirmation step, since this is the first *irreversible* command the app has.

- **`rm [-r] <path>` (`lib/command-line/parse.ts`, `execute.ts`)** — resolves the path, then: refuses if the actor lacks `manage` on the target; refuses a non-empty folder/server unless `-r`/`-R`/`--recursive` is given; refuses to delete the root (nowhere to fall back to). Otherwise returns a `confirm` result naming the node (and, for `-r`, how many items are inside it) rather than deleting immediately.
- **This is the first command wired to real permission checks.** `mv`/`cp`/`create` still skip permission checks entirely (unchanged, still flagged below); `rm`'s `manage` check uses the `PermissionService` that's existed in `packages/core` since Phase 0 but had no caller until now — `ExecuteContext` gained `permissions`/`actor` fields, and `lib/session.ts` gained `CURRENT_ACTOR` (bob, no roles) alongside the existing `CURRENT_AVATAR_ID`/`CURRENT_USER_ID` stand-ins.
- **Confirmation is a UI-level second Enter, not a browser dialog** — a new `CommandResult` kind, `confirm`, carries the exact same command with `confirmed: true` already set. `CommandPrompt` shows it (amber, like an error) and keeps the typed text visible; pressing Enter again re-runs that exact command (skipping `parse` entirely, so it can't drift from what the warning said); typing something else or Escape abandons it. `useCommandLine` now accepts an already-parsed `Command` as well as a raw string, to support this replay.
- **Recursive delete** walks the subtree deepest-first (`deleteSubtree`, the same shape as the existing `copySubtree`, in reverse) and counts descendants up front (`countDescendants`) so the confirmation can say "and 3 items inside it" instead of just "trust me."
- **Mock seed** — `NODE_PROJECTS` now grants bob (`USER_BOB`) an explicit `manage` ACL entry. Without it, `rm` would be permission-denied for every single node in the seed when acting as bob, since alice owns everything else and no other ACL grants `manage` — this was needed to make the happy path demoable at all, not just theoretically correct.
- **Known limitation, flagged rather than fixed:** a recursive delete checks `manage` only on the top-level target, not on each descendant. A nested node that breaks inheritance and excludes the actor could still be swept away by `rm -r` on an ancestor the actor can manage. Consistent with the broader "permissions aren't fully wired in yet" gap on `mv`/`cp`/`create` — not a new hole `rm` introduces, but worth fixing whenever that gap gets closed generally.
- **Scope for later slices:** permission checks on `mv`/`cp`/`create`; per-descendant permission checks on recursive delete; an undo/trash window (there is currently none — confirmed deletes are final).
- Verified: `typecheck`, `lint`, `build`, and `pnpm test` (new parse/execute cases, including a permission-denial case and a "manage via ACL grant, not ownership" case) all green.

### 2026-08-05 — Phase 1 (slice 8): `rename` command, plus `mv` doubles as rename

Closed the one real gap identified when auditing "are basic commands done": `mv` looked like it should double as rename (Linux's `mv old new` renames in place), but it didn't — `mv`'s destination had to already resolve to an existing folder, so `mv frontend frontend-v2` just errored with "path not found." Same shape of fix as `create`/`mkdir`: a dedicated command as the clear, simple way to do the one thing, plus the existing power-user command (`mv`) extended to cover it too.

- **`rename <path> <new-name>` (`lib/command-line/parse.ts`, `execute.ts`)** — quote-aware two-argument parse (like `mv`/`cp`, since both the path and the new name can contain spaces). Resolves the path, then `repo.update(id, { name })`; a no-op if the name is unchanged. Root is renameable (unlike `rm`, renaming isn't destructive — there's no "nowhere to fall back to" concern).
- **`mv` extended to match Linux's actual behavior.** New helper `resolveMoveDestination`: if the whole destination path already resolves to a folder, that's the existing "move into it, keep the name" behavior (unchanged). If it doesn't resolve, the path is split at its last segment (`splitLastSegment`) — everything before it must resolve to a folder, and that last segment becomes the new name. This makes `mv frontend frontend-v2` a same-folder rename, and `mv frontend archive/frontend-v2` a move *and* rename in one step, exactly like Linux's `mv`. The plain-move, non-folder-destination, and can't-move-into-own-subtree error cases are all unchanged and still covered by the existing tests.
- **Cache invalidation gap this surfaced:** renaming changes a node's own `name`, not just its position in the tree, so invalidating `['children', parentId]` (the mechanism `mv`/`cp`/`create` already use) isn't enough — a node's own cached data (`['node', id]`, read directly by the chat header and the tree sidebar's root label) and the current view's breadcrumb (`['ancestors', currentNodeId]`, in case you renamed something you're currently nested under) would otherwise go stale. Added `renamedNodeId?: NodeId` to the `info` `CommandResult`; `use-command-line.ts` invalidates both of those additionally when it's set. `mv` sets it too, when it renamed as part of a move.
- **No permission check** — kept consistent with `mv`/`cp`/`create`'s existing (documented) gap rather than special-casing `rename` the way `rm` was; see the open items already logged under slice 7 and in `roadmap.md`.
- Verified: `typecheck`, `lint`, `build`, and `pnpm test` (new parse cases for `rename`; execute cases for `rename`, `mv`-as-rename, and `mv`-move-and-rename, plus a check that a plain move leaves `renamedNodeId` unset) all green.

### 2026-08-06 — Phase 1 (slice 9): Drag-to-reorder in the folder view

- **`positionBetween` (`lib/tree-position.ts`)** — the fractional-index "midpoint" function `appendPosition`'s comment had deferred: given two neighboring siblings' positions (or `undefined` for the start/end of the list), returns a new position that sorts strictly between them, by walking both strings one base-36 digit at a time and inserting the halfway digit where they first diverge. This is what makes inserting *in the middle* of an ordered list possible, not just appending at the end.
- **`FolderView` rows are now draggable.** Native HTML5 drag-and-drop (no new dependency) — dragging a row over another shows a teal line above/below it depending on which half of the row the cursor is over, and dropping computes the new position from the drop target's current neighbors via `positionBetween`. The dragged row dims while in flight.
- **`useReorderNode` hook** — same optimistic-update shape as `useSendMessage`: re-sorts the cached `['children', parentId]` list instantly, rolls back on error, reconciles on settle.
- **Scope:** same-parent reordering only, in the center-pane folder view. The tree sidebar isn't drag-reorderable yet (nested/recursive drop targets are a bigger chunk of scope, deferred). No permission check — consistent with the existing (flagged) gap on `mv`/`cp`/`create`/`rename`.
- Verified: `typecheck`, `lint`, `build`, and `pnpm test` (7 new `positionBetween` tests) all green, plus an end-to-end Playwright drag against the running dev server confirming the reorder actually persists in the data layer (not just a visual reshuffle) with no console errors.

### 2026-08-07 — Phase 1 (slice 11): Context menus (right-click)

Mouse-driven access to the mutating command-line verbs, closing the last unchecked box in Phase 1's basic feature set: "the command line stays powerful but not mandatory." First Radix primitives in the repo — `@radix-ui/react-context-menu` and `@radix-ui/react-alert-dialog`, added to `packages/ui` (React 19–compatible, no existing Radix footprint to conflict with).

- **Scope decision, made with the user up front:** the menu covers **Rename**, **Delete**, and **New → folder/server/chat channel/voice channel** — not Move/Copy. `mv`/`cp` both need a destination the user picks, and there's no tree/path-picker UI to drive that from a menu yet; they stay command-line-only until one exists.
- **`packages/ui/src/components/context-menu.tsx` and `alert-dialog.tsx`** — thin styled wrappers over the two Radix primitives, matching the existing Panel-dropdown look (`bg-secondary`, beveled border, `font-mono`, `bg-accent` highlight) so a right-click menu reads as the same design system as `CommandSuggestions`/`CommandResults`, not a bolted-on library default. Root/Trigger/Sub are re-exported directly (`export { Root as X } from '...'`) rather than assigned to a `const`, which avoids a Fast-Refresh lint warning that firing on the const form.
- **`lib/command-line/absolute-path.ts` (`buildAbsolutePath`, tested)** — the key seam that lets a mouse action reuse `executeCommand` unmodified: given a `Node` and its ancestors, builds the same absolute path string (`/projects/frontend`) the command line's `resolvePath` already understands. A context-menu action already holds the target `Node` (not a typed path), so this is how it gets back onto the existing `Command`/`path` contract instead of duplicating `execute.ts`'s logic in a second code path.
- **`hooks/use-node-actions.ts`** — the mouse-driven counterpart to `useCommandLine`: calls the same `executeCommand`, but against an explicit target node rather than the app's globally-navigated "current" node (a right-clicked row can be anywhere in the tree). Any valid node works as `executeCommand`'s `currentNodeId` when the path is absolute, so `rename`/`remove` pass the target's own id; `create` passes the *parent's* id, since `create`'s `Command` shape has no path field and always targets `ctx.currentNodeId` directly. Applies the same `invalidateParentIds`/`renamedNodeId` cache-invalidation contract `useCommandLine` already uses, so a mutation looks identical to React Query regardless of which UI triggered it.
- **`components/node-context-menu.tsx`** — the menu itself: Rename has no UI of its own (it calls back to the row, which swaps its own display for a `RenameInput`); Delete always runs `rm` with `recursive: true` (a right-click has no equivalent of typing `-r`) and, on the `confirm` result `rm` already returns, opens an `AlertDialog` reusing that exact message (`"Delete X and N item(s) inside it? This can't be undone…"`) rather than inventing new copy; the same dialog doubles as an error surface (e.g. a permission-denied `rm`) with a single "OK" instead of a destructive action.
- **`components/rename-input.tsx`** — inline, in-place rename (swap the row's name for a text field, matching standard file-manager/VSCode-explorer UX), not a modal — submits on Enter or blur, backs out on Escape or an unchanged/empty name without calling `rename` at all.
- **"New" creates immediately with a default name** (`New Folder`, `new-channel`, …) rather than opening a text-entry field — reusing Rename for the follow-up edit instead of building a second inline-name-entry mechanism. **Right-clicking a collapsed tree folder and creating inside it auto-expands that row** (`onCreated` callback from `NodeContextMenu` down to `TreeNode`'s existing `expanded` state) — without it, the new node is created correctly but invisible behind the collapsed twisty, which is exactly what an end-to-end Playwright pass caught before this fix landed.
- **No permission checks on Rename/New**, consistent with the existing (documented) gap on `mv`/`cp`/`create`/`rename` from the command line. Delete inherits `rm`'s existing `manage` check for free, since it calls the same `executeCommand` path.
- **Scope for later slices:** Move/Copy via context menu once a destination picker exists; a "New" option on empty folder-view space (today it's row-only, so creating in the *currently open* folder still requires the command line or right-clicking a row inside it); the general permission-aware-UI pass already flagged in the roadmap.
- Verified: `typecheck`, `lint` (zero warnings), `test` (4 new `buildAbsolutePath` cases, 70 total passing), and `build` all green, plus an end-to-end Playwright pass against the running dev server covering both surfaces — tree sidebar and folder view — for create, rename, and delete-with-confirm, with no console errors.

### 2026-08-05 — Fix: stale result blocked live suggestions after running a command

Bug, caught while testing `rename`/`rm` interactively: once any command produced a result (an error, an `rm` confirmation, an `ls` listing…), it stayed pinned on screen — `onChange` never cleared it — so live suggestions (slice 6) couldn't come back for the *next* thing typed until Escape was pressed first. It read as "the hint disappeared."

- **`command-prompt.tsx`** — `onChange` now clears any existing `result` on every keystroke, not just on Enter/Escape. Typing is now always "I'm composing something new": suggestions resume immediately, and this also finally makes the `rm` confirm step behave the way slice 7 described it ("typing something else abandons it") — that only worked via Escape before, not by editing.
- Verified: `typecheck`, `lint`, `build`, and `pnpm test` all green (no new automated test — this is an interaction-state fix in a component with no existing render tests; verified manually).
